# アーキテクチャ

## 置き場所

```
src/
  model/     プロジェクトのデータ。トラック、ノート、ミックス、テンポ。
  plugin/    プラグインのホスティング。VST3 をここに閉じ込める。
  audio/     オーディオデバイスの入出力。リアルタイムスレッドを所有する。
  engine/    再生。トランスポートを進め、モデルの音をプラグインに通して出力に流す。
  api/       外部からの操作を受ける IPC サーバ。
  app/       組み立てと main()。
test/        各層のテスト。src/ と同じ名前のディレクトリに置く。
vendor/      外部から持ってきたもの。VST3 SDK など。
```

迷ったときは「その知識は誰のものか」で決める。ノートの長さを知っているのは model、`IAudioProcessor` の呼び方を知っているのは plugin、バッファのサンプル数を知っているのは audio。

## 依存の向き

```
app → api → engine → plugin
                   → model
                   → audio
```

上から下へのみ依存する。逆流させない。

`plugin` `model` `audio` は互いを知らない。この3つが独立していることが構造の要で、崩すと後から効いてくる。

- `model` が `plugin` を知ると、曲データがプラグインの都合に汚染される
- `audio` が `model` を知ると、リアルタイムスレッドからデータ構造を触ることになる
- `plugin` が `audio` を知ると、プラグインをオフラインでレンダリングできなくなる

## 各層の責務

### model

プロジェクトのデータそのもの。ノート、トラック、テンポ、ミックスの値を持つ。

- 純粋なデータと、その操作だけ。ファイル I/O もリアルタイム処理も知らない
- トラックは**安定した id** で識別する。表示名は別の属性。表示名は音源の名前や後付けの命名で変わりうるので、それをアドレスにすると名前を変えた瞬間に指せなくなる
- 範囲（トラック + 小節の区間）を名指しできる型を持つ。API から「17〜20 小節の drums」を指すため、および UI で選択した範囲をプロンプトに渡すために要る
- 制御スレッドからのみ触る。リアルタイムスレッドには渡さない

### plugin

プラグインを読み込み、鳴らす。

- **VST3 の型を上位層に漏らさない。** `pluginterfaces/` の include はこの層の中だけ。上位層は fuwa 自身のインターフェースだけを見る
- 将来 AU を足す場合はこの層に実装を増やす。上位層は変わらない。ただし使う予定のない AU のために抽象を厚くはしない。VST3 の都合が上に漏れていなければ足りる
- プラグインの GUI（エディタ）もこの層が持つ。macOS の NSView が出てくるので ObjC++ になる

### audio

CoreAudio との境界。デバイスを開き、リアルタイムコールバックを回す。

- **リアルタイムスレッドを所有する唯一の層。** ここで走るコードは確保しない、ロックしない、例外を投げない
- オフラインレンダリングも同じ入り口を通す。デバイスに出すかバッファに書くかの違いだけにする。テストで音を確かめられるのはこれによる
- 上位層のデータ構造を直接触らない

### engine

再生位置を進め、モデルの音をプラグインに通し、出力に流す。

- 制御スレッドとリアルタイムスレッドの橋渡しをする。モデルの変更はロックフリーの受け渡しでリアルタイム側に届ける。リアルタイム側からモデルを読みに行かない
- トランスポート（再生、停止、シーク）を持つ

### api

外部のエージェントと内蔵の UI から操作を受ける。

- モデルを変更し、エンジンに指示を出す。音そのものには触らない
- **内蔵 UI に特権的な経路を持たせない。** UI もエージェントも同じ API を通る。UI にしかできない操作が生まれると、API がプロダクトの本体であるという前提が崩れる

### app

組み立てだけ。各層の生成と寿命の管理、`main()`。ここにロジックを書かない。

## リアルタイムの制約

オーディオコールバックの中では以下を行わない。

- メモリの確保と解放（`new` `delete` `malloc` `std::vector` の伸長、`std::string` の生成）
- ロックの取得
- 例外を投げる
- ファイルやネットワークの I/O
- ログ出力

守れているかは目視に頼らない。リアルタイム側に渡るデータはあらかじめ確保しておき、制御側との受け渡しはロックフリーのキューに限定する。

## サニタイザ

開発用ビルドでは AddressSanitizer と UndefinedBehaviorSanitizer を常時有効にする。

C++ で怖いのは、壊れたメモリを踏んでもその場で落ちず、無関係な場所でしばらく後に落ちること。サニタイザはこれを「壊した瞬間に止まる」に変える。後から入れると既存の検出を潰し切るまで使い物にならない期間ができるので、最初から通しておいて常に緑を保つ。

他人がビルドしたプラグインを読み込むと、プラグイン側の問題が報告されることがある。自分では直せないので、その種のものは抑制リストに入れる。
